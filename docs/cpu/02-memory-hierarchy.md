## CPUから見るとメモリは遠い

前章の最後で「データが届かなければCPUは待つことになる」と書きました。
どれくらい待つのか、数字で確認します。

メインメモリに使われている**DRAM**(dynamic RAM)という種類のメモリは、
読み出しの要求を出してから値が届くまで、おおよそ100ナノ秒かかります。
3GHzのCPUでは100ナノ秒は約300サイクルに相当し、
1サイクルで終わる加算の300倍です。

1章の直喩を延長すると、レジスタが机の上のメモ用紙だとすれば、
メインメモリは、例えば別の階にある書庫のようなものです。
容量はレジスタの数百万倍以上ありますが、1回の読み出しに約300サイクルかかります。

ここで2つの用語を区別しておきます。

- **レイテンシ**(latency): 要求してから最初の結果が届くまでの時間です
- **帯域幅**(bandwidth): 単位時間あたりに転送できるデータ量です

メモリの問題は主にレイテンシです。DRAMの帯域幅は毎秒数十GBと大きいのですが、
最初の1個が届くまでが遅いのです。

## キャッシュ: 小容量で高速なメモリを間に置く

この300サイクルの待ち時間が毎回発生すると、CPUの演算がいくら速くても活かせません。
そこでCPUは、**キャッシュ**(cache)と呼ばれる小容量・高速なメモリを
CPUチップ内に持ち、最近使ったデータの写しを置いておきます。
キャッシュには高価だが高速な**SRAM**(static RAM)が使われます。

多くのCPUではキャッシュは3段構成で、CPUに近い順にL1、L2、L3と呼びます
(Lはlevelの略)。近年の一般的なx86-64 CPUを例に、おおよその数字を挙げます
(段数・容量・共有のしかたはCPUのモデルごとに異なります)。

| 記憶場所 | 容量の目安 | レイテンシの目安 |
| --- | --- | --- |
| レジスタ | 数百バイト | 待ちなし(演算器に直結) |
| L1キャッシュ | 32〜64KB | 約4サイクル |
| L2キャッシュ | 256KB〜2MB | 約12サイクル |
| L3キャッシュ | 数MB〜数十MB | 約40サイクル |
| メインメモリ(DRAM) | 数GB〜 | 約200〜400サイクル |

階層の関係を次の図に示します。

```mermaid
flowchart LR
    core["CPUコア"] <--> l1["L1<br/>小さい・速い"] <--> l2["L2"] <--> l3["L3"] <--> dram["メインメモリ<br/>大きい・遅い"]
```

CPUがデータを読むときはまずL1を探し、なければL2、L3、
最後にメインメモリを参照します。目的のデータがキャッシュに
あることを**キャッシュヒット**(cache hit)、ないことを
**キャッシュミス**(cache miss)と呼びます。
L1にヒットし続ける限り、メモリはほぼレジスタと同程度の速さで読めます。
ミスするたびに、下位の階層のレイテンシが加算されます。

なお、この仕組みはすべてハードウェアが自動で行います。
プログラマにできるのは、**キャッシュヒット率が高くなるデータの並べ方と
アクセスの仕方を選ぶこと**であり、「キャッシュに入れる」命令を書くことでは
ありません。この章の残りでは、その方法を説明します。

## キャッシュライン: 64バイト単位の転送

キャッシュとメモリの間のデータ転送は、1バイト単位ではなく
**キャッシュライン**(cache line)と呼ばれる固定長の単位で行われます。
x86-64では64バイトが標準的です(Apple SiliconなどARM64系には
128バイトのCPUもあります)。以降は64バイトを前提に説明します。

つまり`data[0]`(u64なら8バイト)を1個読むだけでも、
その周囲を含む64バイト(u64なら8要素分)がまとめてキャッシュに格納されます。

このことを実験で確かめます。64MBの配列(キャッシュより十分大きい)に対して、
「全要素を読む」場合と「8要素おきに読む」場合を比べます。
読み出しの回数は8分の1になるので、単純に考えれば時間も8分の1に
なるはずです。実測で確かめます。

<RustPlay snippet="ch02/stride" mode="release" title="読み出し回数を1/8にしたら、1/8の時間になるか?" />

Playground上での筆者の実測では、全要素が約3.7ミリ秒、
8個おきが約5.5ミリ秒でした。読み出し回数を8分の1にしたのに、
**速くならないどころか、むしろ遅くなります**。

u64は8バイトなので、8要素おきのアクセスは
「64バイトごとに1回」、つまり**すべてのキャッシュラインにアクセスします**。
メモリから転送するライン数は全要素の場合と同じです。この実験の実行時間を
決めているのはメモリから転送したラインの本数であり、CPUの加算回数ではありません。

さらに、連続アクセスには2つの有利な要因があります。
1つは**プリフェッチ**(prefetch)です。CPUは「順番に読んでいる」という
規則性を検出すると、要求される前に次のラインを先読みして、
レイテンシを隠します。もう1つはSIMD命令による一括処理で、
これは[4章](/cpu/04-simd/)で扱います。

## 局所性: キャッシュが有効に働く条件

ここまでの仕組みをプログラム側から見ると、
キャッシュが有効に働くコードの条件は2つに整理できます。

- **空間的局所性**(spatial locality): 使ったデータの近くを続けて使う性質です。
  同じラインに格納されているデータは、追加の転送なしに読めます
- **時間的局所性**(temporal locality): 同じデータを短い間隔で繰り返し使う性質です。
  キャッシュから追い出される前なら、再び高速に読めます

逆に、キャッシュが最も有効に働かないのは「次にどこを読むか予測できない」
アクセスです。これも実験で確かめます。同じ配列(64MB)を同じ回数たどりますが、
たどる順序だけを「順番どおり」と「ランダム」で比べます。

<RustPlay snippet="ch02/random" mode="release" title="同じ配列・同じ回数。順序だけを変える" />

筆者の実測(Playground)では、順番どおりが約25ミリ秒、ランダムが約1.7秒で、
**70倍近い差**がありました。ランダム側は1回あたり約110ナノ秒で、
これは冒頭に挙げたDRAMのレイテンシがほぼそのまま現れている状態です。

このコードでは、次に読む場所が`next[pos]`、つまり
**今の読み出しの結果が得られるまで決まらない**ようになっています。
このようなアクセスパターンを**ポインタチェイシング**(pointer chasing)と
呼びます。予測できないのでプリフェッチは機能せず、
1回ごとにメモリのレイテンシ全体がかかります。

## VecとLinkedListの本当の差

ポインタチェイシングの典型例が連結リストです。
`LinkedList`の各ノードはヒープ上の別々の場所に
確保され、次のノードへはポインタをたどって移動します。

<RustPlay snippet="ch02/list" mode="release" title="100万要素の合計: Vec vs LinkedList" />

筆者の実測(Playground)では`Vec`が約0.4ミリ秒、`LinkedList`が約3ミリ秒で、
6倍以上の差がつきました。`Vec`は全要素がメモリ上に連続して並ぶため、
空間的局所性が最大限に働きます。

しかもこの実験は`LinkedList`にとって好条件です。ノードを一気に
作ったので、たまたまメモリ上でほぼ連続に並んでいます。長時間動く
実際のアプリケーションでは、ノードはメモリのあちこちに散らばり、
差はさらに開きます。

要素数の増減が多いから連結リスト、という教科書的な判断は、
現代のCPUではほとんどの場合`Vec`より遅くなります。
[`LinkedList`の公式ドキュメント](https://doc.rust-lang.org/std/collections/struct.LinkedList.html)自身が、
ほぼ常に`Vec`か`VecDeque`のほうが速いと明記しているほどです。

## 構造体のレイアウトとパディング

データの並びについて、さらに細かく見ます。構造体のフィールドは
メモリ上にどう並ぶのでしょうか。

前提となる規則が**アラインメント**(alignment)です。多くのCPUでは、
8バイトの値は8の倍数のアドレスに置く、というように、型ごとに
「置いてよいアドレスの単位」が決まっています。この規則を満たすために
フィールドの間に挿入される、データを持たない隙間を**パディング**(padding)と呼びます。

<RustPlay snippet="ch02/layout" mode="release" title="フィールドの並びとサイズ" />

`u8 + u64 + u16`の合計は11バイトですが、結果は16バイトと24バイトです
(64ビット環境での実測です)。

- `#[repr(C)]`(C言語互換の並び)では宣言順に置くため、
  `a: u8`の後に7バイト、`c: u16`の後に6バイトのパディングが入り24バイト
- Rustの既定のレイアウトでは、コンパイラがフィールドを
  **並べ替えて**パディングを減らし、16バイトに収めます。
  ただし既定レイアウトの結果は言語仕様として保証されておらず、
  コンパイラのバージョンで変わりえます。順序やサイズを固定したいときに
  使うのが`#[repr(C)]`です

1個あたり8バイトの差は、100万要素の`Vec`にすると16MB対24MBの差になります。
同じキャッシュ容量に載る要素数が1.5倍違うということです。

### 使うフィールドだけを連続に並べる

構造体の配列には、もう1つ注意点があります。
一部のフィールドしか使わない走査では、使わないフィールドまで
キャッシュラインに格納されることです。

```rust
// AoS: 構造体の配列 (Array of Structs)
struct Player {
    x: f32,
    y: f32,
    hp: u32,
    name: String, // 24バイト
}
let players: Vec<Player> = /* ... */;
// 座標だけ使いたいのに、hp や name もラインに載ってくる

// SoA: 配列の構造体 (Struct of Arrays)
struct Players {
    x: Vec<f32>,
    y: Vec<f32>,
    hp: Vec<u32>,
    name: Vec<String>,
}
// x だけの走査なら、ラインの64バイト全部が x で埋まる
```

前者を**AoS**(array of structs)、後者を**SoA**(struct of arrays)と
呼びます。座標だけを全件走査する処理では、SoAはキャッシュラインの
64バイトすべてが必要なデータで占められるため、転送効率が上がります。
SoAは、全件走査で頻繁に使うフィールドが一部だけという場面の
設計手段であり、何にでも適用すべきものではありません。SoAは[4章のSIMD](/cpu/04-simd/)や
[GPUのメモリ](/gpu/10-gpu-memory/)でも重要になります。

## まとめ

- メインメモリ(DRAM)のレイテンシは約100ナノ秒で、CPUの加算の数百倍です
- CPUはL1/L2/L3のキャッシュに写しを置いてこの遅さを隠します。
  転送は64バイトのキャッシュライン単位です
- キャッシュを有効に働かせる条件は空間的・時間的局所性です。
  実験では、アクセス順序を変えただけで70倍近い差が出ました
- `Vec`が速いのは要素が連続配置されるためです。
  `LinkedList`の走査はポインタチェイシングそのものです
- Rustコンパイラはフィールドを並べ替えてパディングを減らします。
  頻繁に使うフィールドが一部だけなら SoA も検討します

キャッシュはデータの待ち時間を減らす仕組みでした。
次章では、CPUが命令の処理そのものを流れ作業で重ねて速くする仕組みである、
パイプラインと分岐予測を説明します。ここでも中心になる考え方は予測です。
